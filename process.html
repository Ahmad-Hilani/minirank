1. Plan

Architectural Decisions

  • Plain PHP, no framework. Free models have smaller context windows. A large framework scaffold (Laravel, Symfony) would consume context before writing any business logic. Plain PHP kept every file self-contained and reviewable.
  • SQLite over MySQL. Zero setup — no Docker service needed for the DB, no credentials to manage. One file on disk. The assessment explicitly recommended SQLite for easiest reviewer setup.
  • Separation of concerns. Files organized by responsibility: db.php (schema), auth.php (sessions + CSRF), helpers.php (testable logic), api/*.php (JSON endpoints), *.php (pages). Each file stays under ~120 lines, keeping context small.
  • Server-rendered pages + lightweight AJAX. Initial page load renders HTML server-side (fast, no JS dependency). JavaScript only handles modals, search, and the refresh/trend AJAX calls. This kept the frontend simple without a build step.
  • Incremental commits. Built one layer at a time: DB → seeder → API → frontend → auth → projects → stretch goals. Each layer was tested before moving on.

What I Would Change in Hindsight

  • Extract helpers.php earlier. The trend calculation was initially inline in JavaScript. Extracting it to a PHP function in helpers.php from the start would have made testing trivial and reduced duplication.
  • Build the auth layer first. Adding auth after the UI was working meant rewriting queries to scope by user. Building auth → projects → keywords in order would have been cleaner.
  • Use new sessions per feature. Some sessions got long and the model started losing context. Following the guide's advice more strictly (new session per feature) would have reduced debugging time.

2. Prompts & Fixes

Successful

Prompt 1: Backend Foundation

Session: opencode session

The prompt: "Create the SQLite database connection, seed script with 8 keywords × 30 days of positions, and CRUD API endpoints for keywords. All SQL must be parameterized."

Why it mattered: This was the foundation. Getting the schema, parameterized queries, and REST endpoints right in one pass meant everything built on top was solid.

What the AI got right: Clean schema with foreign keys, consistent bindValue() usage, proper HTTP status codes, JSON responses.

What I caught: The initial DEFAULT (datetime('now')) in the schema threw a PHP SQLite3 error. I caught it during testing and changed to DEFAULT CURRENT_TIMESTAMP for the keywords table and removed the default from positions (handled in application code).
Failed / Divergent

Prompt 2: Frontend with AJAX Refresh

Session: opencode session

The prompt: "Build the keyword list page with CRUD modals, search filter, trend indicators, and a Refresh Positions button that uses AJAX."

What went wrong: The AI generated the refresh endpoint without CSRF protection and without scoping to the authenticated user. It also initially used innerHTML to insert trend text without escaping, though the content was hardcoded strings (not user input).

Mistake caught: The refresh endpoint was a plain POST with no CSRF token verification — any external site could trigger position refreshes for a logged-in user. The endpoint also queried all keywords globally, not scoped to the user.
Fix applied: Added csrf_verify() to the refresh endpoint, added X-CSRF-Token header from the JavaScript side, and scoped the query to p.user_id = :uid. This was caught during the security review before committing.
Successful

Prompt 3: Auth + Multi-Project Architecture

Session: opencode session

The prompt: "Add user registration/login with hashed passwords and session management. Add CSRF protection. Add projects — each user owns projects, keywords belong to a project. Update all API endpoints to scope by user."

Why it mattered: This was the most complex change — touching every existing file. The prompt was structured to list each file that needed updating.

What the AI got right: Clean auth.php with password_hash()/password_verify(), session_regenerate_id(true) on login, CSRF token generation via random_bytes(32), and hash_equals() for timing-safe comparison. All API queries were properly scoped with JOINs through the projects table.

What I caught: The seed script initially didn't create a demo user, making manual testing painful. I added demo user creation (demo@minirank.dev / demo1234) to the seeder and updated the README with credentials.

Working with Free Models

  • Context limits were real. Long sessions (30+ turns) caused the model to forget earlier decisions. Starting a new session per feature was essential.
  • Rate limits (429 errors) happened occasionally. Switching from DeepSeek V4 Flash to Gemini Flash as fallback worked smoothly. Noted in the process doc.
  • Free models produce plausible-looking but incorrect code more often than paid ones. Every diff had to be reviewed — the Review panel was used extensively.
  • Small, focused prompts outperformed large ones. "Implement keyword CRUD with parameterized queries" beat "build the entire backend" by a wide margin.

Key Lessons

  • Plan mode first. Agreeing the schema and architecture in Plan mode before generating code saved 30+ wasted requests.
  • Security review is your job. The AI will happily write SQL injection and skip CSRF. Finding it is the candidate's responsibility — and the assessment notices when you do.
  • Verify everything. Running the app after every step caught issues early. The trend calculation boundary test failure was caught this way.
